## 1. 導入

良いコードとは、他人が読みやすいコードだ。
コードは何度も読まれる。
未来の自分も含めた他者が理解しやすいように書くべき、という方向性は、実務経験からも正しいと感じている。

ただ、書いている最中に「他人視点」で判断するのは難しい。
理解しやすさは、時間を置いてみないとわからない部分が大きい。
私自身、この感覚を掴めるようになるまで4〜5年かかった。
それ以前は、重要でない点に注力してしまっていた。

コードを書き・読む経験を積む中で、ひとつの原則に辿り着いた。
「変数の値を推測しやすくする」だ。
これを軸に考えると、他の方法論の優先度も整理しやすくなる。
このブログでは、この原則について説明する。

## 2. 本論

変数の値を推測しやすくするために、最優先でやるべきは変数自体を減らすことだ。
変数がなければ、推測する必要もない。
コードの規模や用途を問わず有効なアプローチだ。

不要なコード・変数は削除する。
実装はシンプルに保ち、重複するロジックは共通化する。
`map` などを活用して中間変数を減らすことも有効だ。

```diff
- const results = [];
- for (const item of items) {
-   results.push(transform(item));
- }
+ const results = items.map(transform);
```

## 3. まとめ

本質は、手法を暗記することではない。
「変数の値を推測しやすいか」という判断基準を持つことだ。
この基準があれば、どちらの書き方を選ぶか自分で判断できる。
新しい方法論に出会っても、自分でその優先度を導き出せる。
技術は、目的を理解してこそ使える。
