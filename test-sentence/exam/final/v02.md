## 1. 導入

良いコードとは他人が読みやすいコードだ、というのはよく言われますよね。私も実務を重ねる中で、これは本当にそうだなと実感しています。コードは書くよりも読む機会の方がずっと多くて、数ヶ月後の自分や他のチームメンバーが「このコード、何をやってるんだっけ？」となる場面を何度も経験しました。だから書くときは常に「他人が理解しやすいか」を意識しています。

ただ、これが思った以上に難しいんですよね。書いている最中に「他人視点」で判断するのは、やってみると想像よりずっと難しい。コードの読みやすさって、時間を置かないと本当には分からないんです。私の場合、実務を積んでから4〜5年くらいで「あ、ここが重要なんだ」という感覚がようやく掴めてきた気がします。それ以前は正直、あまり重要でない点に注力していたこともあったかもしれません。

いろんな方法論を探しながら実践を繰り返す中で、私が「これだ」と思ったのが「変数の値を推測しやすくする」という原則です。この軸で考えると、他の方法論の優先度もすっきり整理できるようになりました。このブログでは、この原則について書いていきます。

## 2. 本論

推測しなければならない変数の数そのものを減らすことが、まず一番の優先事項だと思っています。変数がなければ推測しなくていいので、当然といえば当然ですよね。

具体的なアプローチとしては、まず不要なコードや変数をどんどん削除することです。実装をシンプルに保つということで、使われていないコードや変数は遠慮なく消していきます。次に、重複ロジックを共通化することも大事です。同じ処理が複数箇所に書かれていると、読む人は「これ同じロジックかな？それとも微妙に違う？」と余計な推測を強いられてしまいます。関数にまとめて一箇所に集約することで、その不安をなくせます。

そして `map` などを使って中間変数を減らすというのも効果的です。たとえばこんなコードがあったとします。

```javascript
// Before
const results = [];
for (const item of items) {
  results.push(item.value * 2);
}
```

これを `map` で書き直すと次のようになります。

```javascript
// After
const results = items.map(item => item.value * 2);
```

ループ外で `results` がミュータブルな状態でさらされている時間がなくなるので、読む人が追わなければならない状態がシンプルになります。規模や用途に関わらず使える考え方で、私は常にこれを意識しています。

## 3. まとめ

大事なのは、特定の手法を暗記することじゃないと思っています。それよりも、明確な判断基準を持つことの方がずっと重要です。「この選択、変数の値を推測しやすくなるかな？」という問いを持っていると、新しい技術やパターンに出会ったときに、自分でその有効性を判断できるようになります。

技術は目的を理解してこそ使いこなせるもので、その本質が分かっていれば、自分でも新しい方法を導き出せるんですよね。
